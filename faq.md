### **Общие вопросы**

**Q: Что такое SPQR и какие его цели и отличительные особенности?**\
**A:** SPQR (Stateless Postgres Query Router) — прокси-роутер предназначенный для горизонтального масштабирования PostgreSQL за счёт шардинга. Разработчики выбрали stateless‑подход, чтобы не хранить в роутере информацию о каталогах, кешах и других состояниях базы. Вместо этого SPQR парсит SQL-запросы и распределяет их по шардам на основе заданных правил (маппинг диапазонов ключей на шарды).

*Цели проекта:*
- Обеспечение наивысшей надежности – использование HA‑кластеров как основы шардинга;
- Нулевое время простоя при переходе между монолитом и шардированным кластером и обратно;
- Оптимизация под OLTP‑запросы с минимальными накладными расходами;
- Миграции должны балансировать нагрузку по шардам и минимизировать блокировки.

*Возможности:*
- Шардирование по диапазону значений или по хэшу: роутер определяет, на каком шарде нужно выполнить запрос.
- Совместим не только с обычным текстовым протоколом PostgreSQL, но и с extended protocol — что позволяет использовать prepared statements и клиентские библиотеки без изменений.
- Работает в сессионном и транзакционном режимах.
- Поддерживает сотни и тысячи роутеров для отказоустойчивости.
- Реализует перебалансировку шардов — миграцию данных между шардами, чтобы равномерно распределить нагрузку.
- Позволяет указать несколько серверов для одного шарда — роутер будет распределять запросы только для чтения среди реплик, автоматически определять где находится мастер.

**Q: Когда использовать SPQR и когда он не подходит?**\
**A:** 

**Используйте SPQR, если:**
- Данные не помещаются в одну машину PostgreSQL (> нескольких Тб).
- Наблюдается деградация по чтению/записи, а предел вертикального масштабирования достигнут.
- Требуется "охлаждение" части данных без потери доступности.
- База уже шардирована и требуется автоматизация решардирования.
- Рекомендуем начинать шардирование при >40 CPU-ядрах, >4 хостах или >600 Гб диска.

**SPQR не подходит, если:**
- Сложные запросы затрагивают несколько шардов (например, JOIN между шардами).
- Транзакции изменяют данные на нескольких шардах.
- Нужна OLAP-нагрузка — используйте **Greenplum**.  

**Q: Поддерживаются ли JSONB и большие объекты?**\
**A:** Да. SPQR полностью совместим с типами данных PostgreSQL, включая JSONB. Учитывайте, что большие объекты могут влиять на производительность сети.

**Q: Чем SPQR отличается от других решений (Citus, ShardingSphere, Neon, Vitess, YDB)?**\
**A:**  
- **Лицензия**: SPQR использует открытую лицензию PostgreSQL (не AGPL как Citus).
- **Производительность**: SPQR оптимизирован для минимального overhead, в отличие от ShardingSphere.
- **Управляемость**: SPQR интегрирован с MDB (установка, мониторинг, обновления).
- **Автоматизация**: Автоматическое определение шарда по тексту запроса, поддержка множества роутеров, инструменты для решардирования.
- **Vs Neon**: SPQR обеспечивает истинное горизонтальное масштабирование через шардирование, в то время как Neon — compute-storage separation с ограниченным масштабированием (~500 ГБ). Neon можно использовать как шард внутри SPQR.
- **Vs YDB**: SPQR решает масштабирование для PostgreSQL без смены СУБД.
- **Vs Odyssey**: SPQR — роутер с встроенным пулингом. Odyssey не требуется для пулинга, но может использоваться для HA-кластеров шардов.

**Q: На каких технологиях построен SPQR и как он настраивается?**\
**A:** SPQR написан на Go и работает на уровне протокола PostgreSQL. Для хранения правил шардирования используется ETCD — распределённая БД, обеспечивающая согласованность с низкой задержкой. Настройка правил осуществляется через административную консоль (работает по протоколу PostgreSQL).

**Q: Почему нужен отдельный роутер, а не модификация драйвера?**\
**A:** Попытки реализовать шардинг внутри драйвера быстро упираются в трудности миграций, перераспределения данных и невозможность изменить код приложения. Прокси между приложением и СУБД позволяет прозрачно перенаправлять запросы и выполнять пере‑шардинг без модификации клиента.

**Q: Можно ли совмещать SPQR с другими решениями и облачными базами?**\
**A:** Да! SPQR совместим с облачными managed-базами (Yandex Managed PostgreSQL, AWS RDS, и др.). Можно использовать Neon как шард для хранения данных, а SPQR — как роутер для распределения запросов.

**Q: Как начать использовать SPQR и какие преимущества управляемого сервиса?**\
**A:** Обратитесь в поддержку MDB с пометкой "SPQR". Команда MDB предоставляет: развёртывание и настройку кластера, автоматические обновления, консультационную поддержку, мониторинг ресурсов, и в ряде случаев — разработку недостающей функциональности.

### **Безопасность и эксплуатация**

**Q: Не утекают ли учётные данные через роутер?**\
**A:** Риски аналогичны использованию пулера подключений (например, Odyssey). Данные передаются через SPQR, но практики безопасности соответствуют стандартам Managed Databases (MDB).  

**Q: Кто отвечает за эксплуатацию SPQR?**\
**A:** SPQR не отвечает как устроена эксплуатация шардов. С точки зрения SPQR, шарды это просто connection string. Мы рекомендуем строить отказоустойчивый PostgreSQL кластер на основе Odyssey/PgBouncer, PgConsul/Patroni. 

**Q: Как обеспечить отказоустойчивость SPQR?**\
**A:**  
- Добавьте минимум 3 роутера в разных зонах доступности.  
- Настройте алерты на метрики (CPU, подключения, ошибки).

**Q: Q: Что происходит при перегрузках?**\
**A:** Это зависит от типа нагрузки. Пример: 95% запросов пишущие, а 5% читающие. Если [параметр конфигурации роутера](https://pg-sharding.tech/configuration/router#query-routing-settings) `default_target_session_attrs` = `read-only`, тогда читающие запросы равномерно распределяются между репликами. Если в какой-то момент мы понимаем, что реплика становится недоступной (`SELECT pg_is_in_recovery();` не выполняется за X мс), то мы перестаем отправлять запросы и в фоне проверяем ее статус. Как только обнаружим что реплика снова отвечает, то продолжим отправлять на нее запросы.

**Q: Как обрабатывать отмену запросов (cancel)?**\
**A:**  
- Избегайте частых cancel-запросов: они вызывают переподключения и нагрузку на TLS handshake.  
- Настройте в приложении таймауты больше 50 мс (рекомендуется 100+ мс).  

**Q: Есть ли риски дублирования запросов при использовании балансировщика перед роутерами?**\
**A:** Да. Если клиент разрывает соединение и балансировщик повторяет запрос, SPQR обработает его как новый, что может привести к дублированию (например, для `INSERT`). Рекомендуется использовать идемпотентные операции или реализовать механизм дедупликации на уровне приложения.

**Q: Как настроить резервное копирование?**\
**A:** PITR всего кластера SPQR состоит из PITR шардров и POTR метаданных самого SPQR, то есть etcd который используется под капотом. Для этого мы рекомендуем воспользоваться WAl-G.

**Q: Как диагностировать проблемы и получить статистику?**\
**A:** Включите debug-логирование в конфиге роутера и используйте параметр `/* __spqr__reply_notice = true */` для детализации ошибок. Роутер предоставляет административную консоль по протоколу PostgreSQL с командами `SHOW` для получения статистики (например, `SHOW clients WHERE dbname = testdb;` или `SHOW shards`).

**Q: Как настроить логирование и трассировку?**\
**A:** В конфигурации роутера задаётся `log_level` (debug, info, warning, error, fatal) и `pretty_logging` для структурированного вывода. Для детальной отладки включите `pgproto_debug` и настройте `notice_message_format`. Сообщения `NOTICE` отключены по умолчанию (`show_notice_messages`). Для трассировки используйте опцию `with_jaeger` в `feature_flags` и метрики `time_quantiles`.

### **Распределенные запросы и транзакции**

**Q: Как SPQR обрабатывает SQL-запросы?**\
**A:** A: SPQR обрабатывает SQL-запросы по-разному, в зависимости от их типа и контекста:
1. Обычные запросы: SPQR парсит запрос, определяет таблицу, колонку и значение, к которому происходит обращение. Эти данные сопоставляются с заранее заданными правилами шардирования (например, по ключу или диапазону). На основе этих правил система определяет целевой шард, на который нужно отправить запрос.
2. Запросы с настройками роутинга: На маршрутизацию запроса могут влиять специальные хинты (подсказки), которые указываются в виде комментариев в SQL-запросе или в конфигурации роутера.
3. Транзакции: При получении команды `BEGIN TRANSACTION` SPQR не выполняет запросы немедленно. Вместо этого он сохраняет все последующие запросы (например, `SET` команды) в памяти. Вся транзакция отправляется на конкретный шард целиком только тогда, когда поступает запрос, для которого можно однозначно определить целевой шард. Это позволяет выполнить всю транзакцию на одном шарде.

**Q: Как работают транзакции с несколькими шардами?**\
**A:** Для атомарных кросс-шардовых транзакций используйте двухфазный коммит (2PC):  
1. В начале сессии: `SET __spqr__commit_strategy TO '2pc'`.
2. Либо добавьте `/* __spqr__commit_strategy: 2pc */` к `COMMIT`.
3. Убедитесь, что на шардах включен `max_prepared_transactions` > 0.\
   *Примечание:* Без 2PC изменения могут быть частично применены.

**Q: Можно ли выполнять запросы, затрагивающие несколько шардов?**\
**A:** Да, но с ограничениями:
- Для кросс-шардовых операций используйте комментарий `/*__spqr__engine_v2: true*/` в запросе.
- Операции `COPY` поддерживаются с комментарием `/*__spqr__allow_multishard: true*/`.
- Транзакции, изменяющие данные на нескольких шардах, не поддерживаются.

**Q: Как принудительно указать, на каком шарде выполнить запрос?**\
**A:** Роутер поддерживает виртуальные параметры (хинты). Их можно задавать комментариями в SQL или через SET. Основные хинты: - `__spqr__execute_on` — указывает конкретный шард для выполнения запроса;
- `__spqr__distribution` — выбирает распределение для маршрутизации;
- `__spqr__scatter_query` — заставляет отправить запрос на все шарды.

**Q: Какие стратегии фиксации транзакций поддерживаются?**\
**A:** Хинт `__spqr__commit_strategy` определяет способ фиксации в распределённой транзакции. Возможные значения: `1pc` (однофазная фиксация, она же best-effort) и `2pc` (двухфазная фиксация). Для `2pc` требуется включить хинт `/* __spqr__engine_v2: true */` и установить параметр PostgreSQL `max_prepared_transactions` на всех шардах.

**Q: Как работать с reference-таблицами (справочниками)?**\
**A:** Reference-таблицы реплицируются на все шарды. Создание: `CREATE REFERENCE TABLE table_name (...);` или через распределение: `CREATE DISTRIBUTION ds_repl COLUMN TYPES ... REPLICATED;` и `ALTER DISTRIBUTION ds_repl ATTACH RELATION table_name ...;`. Данные автоматически реплицируются на все шарды. Для записи используйте `/* __spqr__engine_v2: true */`.

**Q: Можно ли шардировать связанные таблицы по одному ключу?**\
**A:** Да! SPQR позволяет хранить связанные данные из разных таблиц на одном шарде, что упрощает JOIN-операции в пределах шарда.

**Q: Поддерживает ли SPQR распределённые последовательности (sequences)?**\
**A:** Да, через команду `CREATE REFERENCE TABLE ... AUTO INCREMENT`. SPQR гарантирует уникальность ID на уровне кластера.

**Q: Как выполняются запросы без явного ключа шардирования?**\
**A:** По умолчанию мультишардовые запросы (без ключа) запрещены. Их можно разрешить с помощью комментария `/* __spqr__scatter_query: true */` в запросе. Результаты с каждого шарда склеиваются, но без гарантии консистентности.

### **Подключение и аутентификация**

**Q: Как подключиться к SPQR?**\
**A:** Роутер использует стандартный протокол PostgreSQL. Приложение не отличает SPQR от обычного кластера и может использовать psql или любой драйвер, указав host и порт роутера. Для административной консоли используется отдельный порт, который указан в конфигурации (поле `admin_console_port`). Пример подключения к консоли: `psql host=localhost sslmode=require user=demo dbname=demo port=6432`.

**Q: Как управлять пользователями и правами?**\
**A:** Пользователи создаются на каждом шарде отдельно. Для централизованного управления используйте скрипты или Terraform. Права на схемы (`GRANT`) выдаются вручную.

**Q: Как работают session и transaction pooling?**\
**A:** Роутер поддерживает режимы pooling, аналогичные Odyssey и PgBouncer. Они задаются параметром `pool_mode` в frontend‑правилах и могут принимать значения `SESSION` или `TRANSACTION`. В режиме `SESSION` одна клиентская сессия закрепляется за одним серверным соединением; в режиме `TRANSACTION` соединение возвращается в пул после каждой транзакции.

**Q: Какие опции есть для управления маршрутизацией соединений?**\
**A:** Через хинт `__spqr__target_session_attrs` или параметр `target_session_attrs` можно указать желаемый тип сервера: `read-write`, `smart-read-write`, `read-only`, `prefer-standby` или `any`. Например, `read-only` позволяет подключаться только к репликам, `prefer-standby` выбирает реплику и переключается на primary при отсутствии реплик. Это полезно при наличии нескольких серверов и фейловере.

**Q: Поддерживаются ли внешние драйверы (pgx, JDBC и т.д.)?**\
**A:** SPQR работает на протоколе PostgreSQL, поэтому большинство драйверов совместимы. Однако при использовании библиотеки `pgx` запросы могут зависнуть из‑за специфики реализации старта соединения через роутер. В таких случаях рекомендуется тестировать драйверы и сообщать разработчикам о найденных проблемах.

### **Производительность**

**Q: Какая производительность у SPQR по сравнению с ванильным PostgreSQL?**\
**A:**  
- В тестах SPQR демонстрирует снижение производительности на **\~10-30%** в зависимости от типа нагрузки против ванильного PostgreSQL.
- Команда активно работает над оптимизацией.

**Q: Как оптимизировать производительность и загрузку данных в SPQR?**\
**A:**  
- Увеличьте ресурсы роутеров (CPU/RAM) при высокой нагрузке.
- Избегайте частых переподключений: настройте пул соединений в приложении.
- Для загрузки больших объёмов используйте `COPY` с комментарием `/* __spqr__allow_multishard: true */` и разбивайте данные на пакеты (например, по 100k строк).
- Отключите debug-логирование и `show_notice_messages: false` для снижения нагрузки на CPU.
- Для CSV-файлов: `\copy table_name FROM 'data.csv' WITH DELIMITER ',' /* __spqr__allow_multishard: true */;`
- Увеличьте `connection_limit` роутеров при ошибках "too many connections".

**Q: Как снизить задержки при чтении и работе с большими результатами?**\
**A:**  
- Избегайте `SELECT *` на больших таблицах. Используйте фильтрацию по ключу шардирования.
- Включите чтение с реплик: `SELECT * FROM table /* target-session-attrs: read-only */;`
- Для batch-операций используйте `COPY` вместо `INSERT`.
- Увеличьте `max_connections` для пользователя.
- В конфигурации укажите несколько серверов для шарда. Роутер автоматически распределит read-only запросы между репликами.
- Настройте `target-session-attrs`: `read-write` (к мастеру), `read-only` (к репликам), `any` (к любому узлу).

**Q: Как ограничить нагрузку от загрузки данных?**\
**A:**  
- Создайте отдельного пользователя с ограничением подключений (`conn_limit`).
- Используйте выделенный роутер для ETL-операций.
- Настройте `session_duration_timeout` для автоматического завершения долгих сессий.

**Q: Какие ресурсы требуются для роутеров и координаторов?**\
**A:** Требования зависят от нагрузки. Для высоких RPS (100K\+) рекомендуются мощные CPU (например, Intel Ice Lake) и достаточная память (16\+ GB). Для примера вот рекомендуемые конфигурации при нагрузке в 20 000 RPS:

Минимальный:
- 3 роутера по 4 vCPU, 100% vCPU rate, 16 ГБ RAM
- 3 координатора по 1 vCPU, 100% vCPU rate, 4 ГБ RAM
- Итого 15 vCPU, 100% vCPU rate, 60 ГБ RAM

Оптимальный:
- 3 роутера по 4 vCPU, 100% vCPU rate, 16 ГБ RAM
- 3 координатора по 2 vCPU, 100% vCPU rate, 8 ГБ RAM
- Итого 18 vCPU, 100% vCPU rate, 72 ГБ RAM

C запасом:
- 5 роутеров по 4 vCPU, 100% vCPU rate, 16 ГБ RAM
- 3 координатора по 2 vCPU, 100% vCPU rate, 8 ГБ RAM
- Итого 26 vCPU, 100% vCPU rate, 104 ГБ RAM

### **Миграция данных и балансировка**

**Q: Как шардировать существующую базу?**\
**A:** Этапы:  
1. Подключите текущий кластер как первый шард.
2. Определите ключ шардирования для таблиц.
3. Создайте key range, покрывающие весь диапазон
4. Добавляйте новые шарды через `REDISTRIBUTE KEY RANGE`.

**Q: Как настроить подключение приложения к SPQR?**\
**A:**  
- Используйте стандартные PostgreSQL-драйверы (например, `pgx`).
- В конфигурации укажите все роутеры кластера.
- Включите `__spqr__engine_v2: true` для сложных запросов (например, с CTE).

**Q: Как выбрать ключ шардирования?**\
**A:**  
- Используйте колонку с равномерным распределением (например, `user_id`).
- Для строк: `varchar` с хеш-функцией (`CITY`, `MURMUR`).
- Избегайте колонок с `NULL` или часто изменяемыми значениями.

**Q: Как шардировать по составному ключу (по нескольким колонкам) ?**\
**A:**
Без хэша
```sql
CREATE DISTRIBUTION ds1 COLUMN TYPES integer, varchar;  
ALTER DISTRIBUTION ds1 ATTACH RELATION orders DISTRIBUTION KEY user_id, order_date; 
```

С хэшом
```sql
CREATE DISTRIBUTION ds COLUMN TYPES varchar HASH, int HASH;
ALTER DISTRIBUTION ds ATTACH RELATION table DISTRIBUTION KEY col1 HASH, col2 HASH;
```

**Q: Как создать "шард по умолчанию" для непривязанных ключей?**\
**A:** Используйте команду `ALTER DISTRIBUTION {distribution_id} ADD DEFAULT SHARD {shard}`

**Q: Как добавить новый шард и перебалансировать данные?**\
**A:**  
1. Добавьте новый шард в router.yaml / coordinator.yaml или с помощью `ADD SHARD`.
2. Перераспределите диапазоны ключей. Используйте команды: `SPLIT KEY RANGE` (разделить диапазон), `MOVE KEY RANGE` (переместить диапазон, требует блокировки), `REDISTRIBUTE KEY RANGE` (автоматический перенос данных).
3. Используйте `SYNC REFERENCE TABLES` для копирования справочных таблиц.

Ребалансировка может быть автоматической (на основе нагрузки CPU/диска, ε-split) или ручной. Автоматическое управление находится в стадии тестирования и пока не рекомендуется в production. Для ускорения миграции больших объемов: увеличьте размер чанка, убедитесь в наличии индекса по ключу шардирования, избегайте параллельных операций записи.

**Q: Как управлять схемой данных (DDL)?**\
**A:** Все DDL-операции (`CREATE/ALTER`) автоматически реплицируются на шарды. Для кросс-шардовых DDL используйте `ALTER TABLE ... /* __spqr__multishard_ddl: true */;`. Переименование таблиц: выполните `ALTER TABLE` в одной транзакции с комментарием `/* __spqr__allow_multishard: true */` (требуется SPQR ≥ 1.5.0).

**Q: Какие типы данных поддерживаются для шардирования?**\
**A:**  
- Целочисленные (`int`, `bigint`).
- Строки (`varchar`).
- UUID.
- Хеш-функции: `CITY`, `MURMUR` (только для целых чисел). **Пользовательские хеш-функции не поддерживаются**.
- Составные ключи.

**Q: Можно ли выполнять JOIN между шардами?**\
**A:** Нет. JOIN возможен только в пределах одного шарда. Для связанных данных используйте колокацию (хранение связанных таблиц на одном шарде через общий ключ шардирования).

**Q: Поддерживаются ли кросс-шардовые транзакции?**\
**A:** Только для операций чтения. Запросы, изменяющие данные на нескольких шардах, не поддерживаются. Исключение: реплицированные таблицы (reference tables) с `/* __spqr__engine_v2: true */`. Также поддерживается команда `COPY` с комментарием `/* __spqr__allow_multishard: true */`.

**Q: Как SPQR управляет лимитами подключений?**\
**A:** Ограничения на уровне роутера (rate limits, квоты для пользователей) планируются, но пока не реализованы.

**Q: Есть ли дедупликация запросов? Какая политика повторных попыток (retry) используется?**
**A:** Нет. Если клиент отваливается и повторяет запрос, роутер обработает его как новый. Планируется добавить настраиваемые стратегии.

**Q: Поддерживаются ли операции DDL (например, ALTER TABLE, RENAME) в транзакциях?**\
**A:** Частично. Некоторые операции DDL могут выполняться в транзакциях, но для кросс-шардовых DDL (например, переименование таблиц на нескольких шардах) требуется включение специального режима (в разработке). Рекомендуется выполнять такие операции вне транзакций или с осторожностью.

**Q: При выполнении запроса возникает ошибка `error processing query ... : syntax error`. Что делать?**\
**A:** Эта ошибка обычно означает внутреннюю проблему SPQR а не синтаксическую ошибку в вашем SQL-запросе.

1. Сообщите разработчикам SPQR:
- Приложите полный текст запроса.
- Версию SPQR и PostgreSQL.
- Конфигурацию шардирования.
2. Временное решение:
- Проверьте запрос на совместимость с документацией SPQR.
- Упростите запрос (разбейте на части, уберите сложные конструкции).

Почему возникает эта ошибка? SPQR использует собственный парсер SQL, который может не поддерживать некоторые нюансы:
- Специфические операторы PostgreSQL.
- Редкие варианты синтаксиса.
- Нестандартные функции.
