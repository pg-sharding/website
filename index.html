Frequently Asked Questions

When should I use SPQR?

SPQR is ideal when:

  • Your data exceeds several terabytes and doesn't fit on a single PostgreSQL instance
  • Most queries operate within a single shard (not requiring cross-shard joins)
  • You need 100K+ queries per second with consistent latency
  • You want to automate resharding and load balancing

How is SPQR different from Citus or Vitess?

SPQR is a stateless router focused on OLTP workloads with true open source licensing (PostgreSQL License, not AGPL). It automatically determines shards from query text without manual hints, supports multiple router instances for high availability, and includes built-in tools for resharding and data migration.

Can I use SPQR with managed PostgreSQL services?

Yes! SPQR works with any PostgreSQL-compatible database, including managed services like Yandex Managed PostgreSQL, AWS RDS, Google Cloud SQL, and Azure Database for PostgreSQL.

What about cross-shard queries and transactions?

SPQR supports cross-shard reads with the /*__spqr__allow_multishard: true*/ hint. For atomic cross-shard writes, use two-phase commit (2PC) by setting __spqr__commit_strategy to '2pc'. However, SPQR is optimized for single-shard transactions.

How does performance compare to vanilla PostgreSQL?

In TPC-C benchmarks, SPQR shows approximately 50% overhead compared to a single PostgreSQL instance. However, by distributing load across multiple shards, total throughput scales linearly with the number of shards.

Can I migrate an existing database to SPQR?

Yes! Start by connecting your current cluster as the first shard, define your sharding key, then use SPQR's built-in tools to gradually migrate and reshard data. The process can be done with minimal downtime.
